# 材质、编辑器导入与验收要求

## 材质链路

现有车辆的外观是 **GLB 网格/顶点色 + 编辑器原生材质 + Lua 槽位配置** 的组合。单独在 Blender 打开 GLB，效果可能与游戏不同；GLB 不包含编辑器运行时的全部材质参数覆盖。

- 现有主要 Shader 为 `Douyin/AI/PBR/EnvLit_AI` 及 AlphaBlend 变体。实际移动端可能使用原生兼容变体，应保留加载成功的源材质，而不是强求完全相同的 Shader 名称。
- 当前服务通过 `Material(source)` 克隆已加载的原生源材质，保留纹理、UV 偏移/缩放、队列和关键字，再处理有记录的外观参数。不要回退成 `Shader.Find + Material(shader)` 后只写颜色/浮点数。
- 常见原生贴图属性为 `_BaseTex`、`_ORM`、`_Normalmap`；不是凭惯例假设 `_BaseMap`。不同 Shader/变体需要枚举实际属性。导入新贴图时要同时检查颜色空间、法线方向、ORM 通道约定和 UV，不能只靠属性名字推断通道含义。
- 保留 `COLOR_0` 等顶点属性。原生 `_USEVERTEXCOLOR_ON` / `_USEVERTEXCOLOR1_ON` 关键字与透明变体会影响结果；未验证前不要删顶点色、统一透明材质或把所有材质合为一个槽。
- 当前材质变量解析器不支持 `---@var sourceMaterials:UnityEngine.Material[]` 的公开绑定方式，不能照抄该旧方案作为可靠打包措施。新纹理必须通过编辑器支持的资产导入和明确资源引用进入包，或用已验证支持的绑定类型另行接入。
- `manifests/assets.json` 的 `images/textures` 给出每个实际 GLB 的贴图载荷数量。未来加贴图后须重新统计，确保资源被打包；Lua 不能从颜色参数复原未入包的纹理。

## 材质预备机制

现有服务在 Awake 开始预备，按帧预算分批克隆/匹配；只暂时关闭外观 Renderer 的显示，保留车辆根、座位、刚体和交互。当当前车辆所有部件材质与属性确认后才释放显示，并有资源异常的超时保护。

美术升级不要删除 `geocore-material-lifecycle.lua` 或自行修改 `forceRenderingOff`；否则可能再次出现进场几秒后从异常材质恢复的闪变。不可跨不同纹理和 UV 组合共用同一材质实例。

## 导入步骤

1. 先备份原工程，在原车辆根下替换视觉部件。保留根节点、脚本绑定、碰撞结构和座位，不直接删掉原根重新导入一辆“无逻辑车”。
2. 以本包 catalog 样件作参照导出 GLB；合并自包含资源，避免本机绝对路径纹理。先导入一辆验证坐标、比例和材质，再批量。
3. 选中资产检查是否保留分件和层级；原生导入可能规范化比例，应使用世界尺寸复核。复用已有根缩放，不把二次自动缩放叠加进去。
4. 对照每车 `scene-nodes.json` 恢复部件变换及脚本挂点。`glbSliceData.slicePath` 指向原 GLB 的层级索引，改 GLB 层级后要重新建立，不能复用旧 slicePath。
5. 在节点组件中核对脚本 ID 与参数。GLB 内的历史 Lua extras 不是当前版本的权威来源，防止产生重复驾驶或旧版材质服务。
6. 按新拓扑更新材质服务的部件匹配与槽映射。不能把编辑器 `appearanceData` 的颜色覆盖当作唯一材质来源；在编辑器里保存后还要复核，因为保存可能规范化这些字段。
7. 保存后用正式资源上传链路生成开发包，手机端重新冷启动验证。编辑器正确不代表手机 Shader 和纹理依赖已入包。

## 验收项

| 类别 | 要通过的检查 |
|---|---|
| 外观 | 16 车同镜头对比，无纯色透明壳、紫色材质、丢贴图、错误顶点色；低座舱符合原设定 |
| 几何 | 车身、轮胎不重复渲染；轮胎绕轴转动，不偏移、不绕大圈；座位不悬空 |
| 行为 | 本体与变身后均可上下车，驾驶/乘坐分清；手机交互按钮正常 |
| 比赛 | 原准备阶段统一发车；人车共同传送；比赛门、计时、结算回位保持原规则 |
| 生命周期 | 首次加载、重新启用、网络对象复制后的材质正确；错误日志无新增 |
| 性能 | 记录新旧 GLB、纹理内存、Renderer/材质槽和三角面数量；手机同镜头比较，不以编辑器帧率代替真机结果 |

本次打包仅验证文件完整性和引用可追溯性，**没有把升级模型导回工程、没有重新上传游戏，也没有重新完成上述运行验收**。这些是美术升级后的接入验收要求。
